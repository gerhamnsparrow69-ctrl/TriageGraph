8. TESTING

The brief asks for at least 15 meaningful test cases. We planned 32, grouped as normal, boundary,
invalid input, exception, authorisation, business-rule and architecture cases, and each one names
the JUnit test that proves it. The full table with scenario, expected result, test name and status is
in docs/test-cases.txt. The whole backend has 683 automated tests; all of them pass under
./mvnw verify (0 failures, 0 errors, 22 Nov 2026).

8.1 How we test

  - Unit tests check one class in isolation: domain rules (state transitions, priority formula,
    assignment strategies, duplicate score), with mocked ports where a module talks to another.
  - Integration tests start the Spring application with an in-memory H2 database and call the REST
    endpoints with MockMvc, so they check JSON, status codes, security and the database together.
  - Contract tests run the same checks against every implementation of an interface. For example,
    AssignmentStrategyContractTest runs one set of assertions against all four assignment
    strategies, which proves the Liskov substitution principle.
  - Architecture tests (ArchUnit) fail the build if a layer breaks a rule: the domain must not
    depend on infrastructure or API code, controllers must not use repositories, modules must not
    form a dependency cycle (TC32).
  - Measured accuracy: the AI features are evaluated on labelled data, not only unit-tested (8.4).

How to run: from the backend folder, ./mvnw verify runs everything. The Surefire reports are in
backend/target/surefire-reports.

8.3 The 32 planned cases

See docs/test-cases.txt. In short:

  - Normal: TC01 to TC06 (report to assigned, priority score, strategies, lifecycle, notification).
  - Boundary: TC07 to TC12 (score 40.0 versus 39.9, user-count bands, 75 % SLA, deadline, duplicate
    threshold, technician at maximum load).
  - Invalid input: TC13 to TC15 (blank description, unknown service, weak password).
  - Exception: TC16 to TC22 (illegal transitions, missing SLA policy, AI failure, SMTP down,
    dependency cycle, repeated submission).
  - Authorisation: TC23 to TC27 (employee on admin endpoints, other people's incidents, lockout,
    expired token).
  - Business rules: TC28 to TC31 (SLA pause, joining a duplicate, root cause ranking, escalation).
  - Architecture: TC32 (layering rules and the tamper-evident audit chain).

8.5 Bugs found while testing

  - Priority score assertion (Member 2): two tests (IncidentControllerTest and
    AuditTrailIntegrationTest) hard-coded the score 83.2, which assumes a service of criticality 4.
    With the real triage the service is rated HIGH, so the score is 62.4 and the priority is still P1.
    The tests now check that a P1 and a number are returned.
  - Triage suggested a category that the incident module rejects (Member 2): the suggestion is now
    always replaced by an active catalogue category (test suggestionIsAlwaysAnActiveCatalogCategory).
  - The stored fix text began with "Resolved:" (Member 2): the knowledge base now strips the prefix
    (test in KnowledgeBaseServiceTest).
  - Join, merge and reassign had no implementation (Members 1 and 2): IncidentCommandService now
    implements the shared port, with IncidentJoinTest covering joinAsAffected.
  - TC13 (Member 1): an impact outside the enum, for example 7, is rejected with 400, but as a
    generic "Failed to read request" ProblemDetail without fieldErrors, unlike the other validation
    errors. The test documents the current behaviour. Mapping unreadable fields to INVALID_INPUT with
    a field error is a small change in GlobalExceptionHandler.

8.6 Known limits of the test suite

  - Gemini is only tested through a local test server and the failure paths (timeouts, 429, invalid
    JSON). We do not call the real Gemini service in tests, so no test depends on the network or an API
    key.
  - Notification delivery is tested through a stand-in mail sender and push gateway, not a real SMTP
    server.
  - The demo accounts and incidents are seeded for the video; the tests create their own data.
