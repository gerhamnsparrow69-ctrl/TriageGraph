1. PROBLEM ANALYSIS

1.1 The problem

A campus IT department (modelled on a CCIT-style setup) runs the services everyone depends on:
single sign-on, the LMS, the ERP, email, hostel Wi-Fi and the fee payment app. When one of them
fails, many people notice at once, and most of them report it separately, by email, phone or a
shared form. The desk then has to work out, by hand and under time pressure:

  - which of the reports are really the same problem;
  - how urgent each problem is, compared with everything else in the queue;
  - who should fix it, and whether they have time;
  - whether it is being fixed within the agreed time, and who to tell if it is not;
  - afterwards, what actually happened and who did what.

Done by hand, each of these goes wrong in a predictable way, which is the starting point for
TriageGraph.

1.3 The solution in one paragraph

TriageGraph is a web-based IT service management platform built as a Spring Boot modular monolith
with a React front end. Every incident follows one lifecycle: Report, Classify, Prioritise, Assign,
Investigate, Resolve, Verify, Close. Two intelligence layers sit on top. Triage intelligence asks
"has this already been reported, and what kind of problem is it?": it suggests the category and
service while the employee types and warns about likely duplicates. Topology intelligence asks "are
these separate problems, or one hidden cause?": it uses the service dependency graph to rank
probable root causes. Both feed back into priority: joining a duplicate raises the affected-user
count, and a service with many dependents has a larger blast radius.


1.4 How the core addresses the challenges

The incident is the centre of the system. Triage, assignment, SLA, notifications and reports all
read or change incidents, so the incident module is strict about its own rules and loose about
everyone else:

  - One aggregate, Incident, owns its state. Status, priority and assignee have no public setters;
    every change goes through a named action (acknowledge, resolve, ...) that checks the rules.
  - Illegal actions are refused with 409 and change nothing (State pattern, section 4.5).
  - Who may act is checked on the incident itself, not only in the user interface: an employee can
    only open incidents they reported or joined, and only the assignee can work an incident.
  - Every change becomes a domain event, and every event becomes a tamper-evident audit entry
    written in the same transaction (section 3.5).
  - Other modules reach incidents only through the contracts in the shared package, so each team
    member could build and test their module independently (section 3.3).


1.5 Assumptions

  - One campus, one IT department, one time zone. Times are stored in UTC and shown in IST.
  - Every user has an account; employees register themselves and staff accounts are created by an
    administrator. There is no integration with the campus directory (LDAP) yet.
  - The application runs on a single campus server. The design keeps module boundaries so it could
    be split later, but nothing currently needs more than one instance.
  - Monitoring data (service health, change records) is entered or seeded, not collected from live
    infrastructure.
  - Text analysis is tuned for English reports.
  - Gemini is optional. With no API key, every feature still works from local models and rules.
