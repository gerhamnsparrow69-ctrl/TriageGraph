### Notes on the Member 3 rows (checked against the code on main, 22 Nov 2026)

1. **TC09 and TC10.** The pure evaluator (`SlaEvaluatorTest`) covers the 75 % and 100 % boundaries, and the persisted clock state feeds the breach report. The live `SlaMonitor` runs every 30 seconds, saves the flags and publishes `SlaWarningRaised` and `SlaBreached` (`SlaModuleTest.warningAndBreachEventsAreNotDuplicated`). There is no end-to-end test of three monitor ticks, and the frozen schema stores breaches in `sla_clocks`, not in a `SlaViolation` table.
2. **TC18.** The provider always supplies defaults for P1 to P4, so a missing P2 policy cannot occur. The test covers a null priority and an unknown service instead, and no admin alert is raised.
3. **TC21.** The graph builder rejects cycles and self-loops with `CyclicDependencyException` (mapped to 422), but the delivered topology API is read-only, so no HTTP request can add a dependency.
4. **TC28.** The evaluator pauses only the resolution clock. The older `SlaClock` test pauses both clocks and does not assert the exact 10-minute shift of the due time.
5. **TC30.** The ranking is covered (Campus SSO about 0.783). Creating a Major Incident with three child incidents is not part of the delivered RCA.
6. **TC31.** M1 tests the incident-level escalation and its event. Nothing in the monitor triggers the +5 minute level 2 to level 3 sequence yet, and there is no end-to-end audit test.

These statuses match section 8.6 of the report. Final Actual and Status values come from the Surefire reports (`backend/target/surefire-reports`).
